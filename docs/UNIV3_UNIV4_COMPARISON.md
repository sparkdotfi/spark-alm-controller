# UniswapV3Facet vs UniswapV4Facet: Functional Comparison

Functional differences between `UniswapV3Facet` and `UniswapV4Facet` as invoked by the `Controller`. Focused on protocol accounting, rate limits, slippage, ownership, and governance.

---

## Functional Difference Matrix


| Category                                 | UniswapV3Facet                                                                                                                        | UniswapV4Facet                                                                                                                                                                                      | Why it matters                                                                                                                                                                                                                     |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Rate-limit key structure**             | `keccak256(limitType, token, pool)` - per-token, per-pool                                                                           | `keccak256(limitType, poolId)` - per-pool only                                                                                                                                                    | V3 allows independent rate limits per asset within a pool. V4 consolidates both assets into a single limit, meaning a large deposit of one token consumes the same capacity as the other.                                          |
| **Deposit rate-limit source**            | Return values from `mint()` / `increaseLiquidity()` - actual amounts consumed by the NFPM                                           | Normalized net balance delta across both tokens, with clamped subtraction                                                                                                                         | V4's balance-delta approach captures any token movement (including fee receipts), but combines both tokens under an equal-value assumption. V3 uses exact per-token amounts as reported by the NFPM.                               |
| **Deposit rate-limit normalization**     | Raw token amounts (e.g., 1e6 for USDC)                                                                                              | 18-decimal normalized, summing both tokens                                                                                                                                                        | V4 rate limits are only meaningful if both tokens are approximately equal in value. Applying V4 to a pool with differently-valued tokens would produce incorrect rate-limit accounting.                                            |
| **Deposit fee netting**                  | Not relevant - return values from mint/increase do not include fee receipts                                                         | Clamped subtraction means fee receipts during deposit reduce the rate-limit decrement (to a floor of 0)                                                                                           | V4 is net-of-fees for deposits. Code comment: "Rate limit decrease is net of any token0 or token1 received due to fees."                                                                                                           |
| **Withdraw rate-limit source**           | Return values from `decreaseLiquidity()` only (not `collect()`)                                                                     | Actual balance deltas (endingBalance - startingBalance) per token, normalized and summed                                                                                                          | V3 rate-limits only the principal portion of the withdrawal. V4 rate-limits the total amount received including accrued fees.                                                                                                      |
| **Withdraw fee inclusion**               | Excluded - fees are collected in a separate `collect()` call and not rate-limited                                                   | Included - balance deltas capture everything. Code comment: "Rate limit decrease includes any token0 or token1 received due to fees."                                                             | V3 fees flow to the proxy without consuming withdrawal rate-limit capacity. V4 fees do consume capacity.                                                                                                                           |
| **Swap rate-limit timing**               | Post-execution, using actual balance delta of tokenIn                                                                               | Pre-execution, using normalized nominal `amountIn`                                                                                                                                                | V3 measures what was actually taken from the proxy. V4 may over-count if the router takes less than `amountIn` (partial fills). Code comment: "Rate limit decrease does not account for the net amount of tokenIn actually taken." |
| **Swap rate-limit denomination**         | Raw token amount of tokenIn                                                                                                         | Normalized 18-decimal amount of tokenIn                                                                                                                                                           | V3 rate limit for a 6-decimal token tracks in 6-decimal units. V4 always tracks in 18-decimal normalized units.                                                                                                                    |
| **Swap price protection**                | TWAP oracle + operator-supplied `tickDelta` to compute `sqrtPriceLimitX96`, plus `minAmountOut`                                     | `amountOutMin` only, plus a governance `maxSlippage` check that validates `amountOutMin` is not unreasonably low relative to normalized `amountIn`                                                | V3 has a hard on-chain price floor/ceiling enforced at the pool level via `sqrtPriceLimitX96`. V4 relies entirely on output-amount minimums with no independent price-level constraint.                                            |
| **Add-liquidity slippage validation**    | TWAP-derived expected amounts; operator `min` must satisfy `min >= expectedAmount * maxSlippage`                                    | Tick-limit constraints on range bounds protect against magnitude of sandwich attacks                                                                                                              | V3 prevents operators from setting dangerously loose minimums. V4 trusts operator-supplied `amount0Max`/`amount1Max` without external price reference.                                                                             |
| **Remove-liquidity slippage validation** | Post-execution check: `minAmount >= (actualAmount * maxSlippage) / 1e18` for each token                                             | None beyond position manager's enforcement of `amount0Min`/`amount1Min`                                                                                                                           | V3 enforces that the operator's declared minimums were not unreasonably loose relative to what was actually received. V4 has no such back-check.                                                                                   |
| **Ownership check on decrease**          | Required (`ownerOf(tokenId) == proxy`)                                                                                              | Intentionally omitted. Comment: "the worst case is that another account's position is decreased or closed by the proxy."                                                                          | V4 allows the proxy to decrease any position in the correct pool. Tokens still flow to the proxy, so no direct value leak, but another user's position can be modified.                                                            |
| **Tick re-validation on increase**       | Requires operator-supplied ticks match position's ticks exactly.                                                                    | Re-checks position ticks against current governance `TickLimits` on every increase. Comment: "it's possible the position was minted under outdated tick limits, or was transferred to the proxy." | V4 is stricter: governance can tighten tick limits and existing positions cannot receive more liquidity if their range is now outside bounds. V3 only validates ticks when the position is first created.                          |
| **Protocol address mutability**          | Router and NFPM are configurable storage variables set by admin                                                                     | `_PERMIT2`, `_POSITION_MANAGER`, `_ROUTER` are hardcoded constants                                                                                                                                | V3 addresses can be upgraded by governance. V4 addresses require a code change to update.                                                                                                                                          |
| **maxSlippage key**                      | `maxSlippages[pool]` where pool is an address                                                                                       | `maxSlippages[address(uint160(uint256(poolId)))]` - truncates bytes32 poolId to address                                                                                                           | V4 truncates a 32-byte pool identifier to 20 bytes for the maxSlippage lookup, using the same shared mapping as V3. This is a collision-theoretic consideration.                                                                   |
| **Tick-range governance**                | `addLiquidityTickBounds.lower` and `.upper` per pool (independent setters); no width constraint                                     | `tickLowerMin`, `tickUpperMax`, and `maxTickSpacing` per poolId (single setter, atomic); includes a maximum width constraint                                                                      | V4 adds a maximum tick-range width parameter that V3 does not have, preventing excessively wide positions. V4's atomic setter prevents inconsistent intermediate states.                                                           |
| **TWAP dependency**                      | Required for swaps and add-liquidity                                                                                                | Not used at all                                                                                                                                                                                   | V3 depends on the pool's oracle accumulator. V4 has no oracle dependency.                                                                                                                                                          |
| **Tick spacing validation on mint**      | Validates `ticks.lower % tickSpacing == 0` and `ticks.upper % tickSpacing == 0`                                                     | No explicit tick-spacing validation (delegated to position manager)                                                                                                                               | V3 does client-side validation that ticks align with the pool's tick spacing. V4 relies on the position manager to reject invalid ticks.                                                                                           |
| **Deadline semantics**                   | Explicit `deadline` parameter passed to all NFPM/router calls                                                                       | Always uses `block.timestamp`                                                                                                                                                                     | V3 supports future deadlines. V4 deadlines are always "this block," meaning the operation must execute in the current transaction.                                                                                                 |
| **Liquidity parameter on deposit**       | Add-liquidity specifies `target` amounts (desired token amounts); liquidity is computed by the NFPM                                 | Mint/increase specifies `liquidity` directly; `amount0Max`/`amount1Max` are caps                                                                                                                  | V3 operators think in token amounts. V4 operators think in liquidity units. This changes the operator interface and the precision of what gets deposited.                                                                          |
| **Return values to caller**              | `addLiquidity` returns `(tokenId, liquidity, amounts)`. `removeLiquidity` returns `amounts`. `swap` returns `amountOut`.            | All functions return `void`                                                                                                                                                                       | V4 does not propagate return values to the caller (Controller). Integrators cannot observe exact amounts consumed or received from the controller's return data.                                                            |
| **Separate fee collection**              | Explicit `collect()` call after `decreaseLiquidity()`                                                                               | No separate collect step - `DECREASE_LIQUIDITY` + `TAKE_PAIR` handles everything atomically                                                                                                       | V3 has a two-step process; V4 is single-step. This affects how fees are accounted (see above).                                                                                                                                     |
| **Equal-value assumption**               | Not present - each token tracked independently                                                                                      | Explicitly assumed. Comments: "the assumption that the tokens are valued equally (i.e. 1.000000 USDC = 1.000000000000000000 USDS)"                                                                | This is a fundamental limitation of V4's consolidated accounting. It is correct for stablecoin pairs but incorrect for pairs with price divergence.                                                                                |
| **Input validation**                     | Facet-level checks on minAmountOut > 0, liquidity bounds, nonzero post-deposit liquidity, and nonzero target amounts.             | V4: Delegates input bounds checking to the position manager / router; facet only validates tick limits and poolId match.                                                                        | V3 reverts earlier with descriptive facet-specific errors. V4 reverts come from external contracts.                                                                                                                              |
