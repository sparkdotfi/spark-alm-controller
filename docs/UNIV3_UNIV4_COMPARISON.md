# UniswapV3Facet vs UniswapV4Facet: Functional Comparison

Functional differences between `UniswapV3Facet` and `UniswapV4Facet` as invoked by the `Controller`. Focused on protocol accounting, rate limits, slippage, ownership, and governance.

Both facets are `Facet` implementations with isolated ERC-7201 storage (`VERSION = "1.0.0"`). Allocator functions require `ALLOCATOR_ROLE`; admin setters require `DEFAULT_ADMIN_ROLE`.

---

## Functional Difference Matrix

| Category                              | UniswapV3Facet                                                                                                                                                                                                                             | UniswapV4Facet                                                                                                                                                                                     | Why it matters                                                                                                                                                                       |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Pool identifier**                   | `address pool` (the V3 pool contract)                                                                                                                                                                                                      | `bytes32 poolId` (`keccak256(abi.encode(poolKey))`, must match `positionManager.poolKeys(bytes25(poolId))`)                                                                                        | Rate-limit keys, governance mappings, and allocator calls all key off different types. V4 operators must derive `poolId` from the canonical `PoolKey`.                               |
| **Rate-limit key helpers**            | `makeAddressKey` / `makeAddressAddressKey`                                                                                                                                                                                                 | `makeBytes32Key` / `makeAddressBytes32Key`                                                                                                                                                         | Same logical limit types (`LIMIT_UNISWAP_V3_*` vs `LIMIT_UNISWAP_V4_*`), different encoding. Limits are not shared across facets.                                                    |
| **Allocator API shape**               | `addLiquidity` (mint or increase via `tokenId == 0`), `removeLiquidity`, `swap`                                                                                                                                                            | `mintPosition`, `increasePosition`, `decreasePosition`, `swap`                                                                                                                                     | V3 uses one deposit entrypoint; V4 splits mint vs increase. Tick/amount parameters differ (see liquidity-parameter row).                                                             |
| **Protocol dependencies**             | Immutable `positionManager` (NFPM), `router` (SwapRouter `exactInputSingle`)                                                                                                                                                               | Immutable `permit2`, `positionManager` (V4 position manager), `router` (Universal Router `execute` with V4 swap command)                                                                           | V4 requires Permit2 for approvals into the position manager and router. Addresses are fixed at deployment.                                                                           |
| **Token approval path**               | `ApproveLib.approve` from proxy → spender (router or NFPM)                                                                                                                                                                                 | `ApproveLib.approve` proxy → Permit2, then Permit2 approval to spender (expiry `block.timestamp`)                                                                                                  | Different approval surface and reset semantics; V4 always routes spend authority through Permit2.                                                                                    |
| **Deposit amount measurement**        | Proxy balance delta per token after NFPM `mint` / `increaseLiquidity` (`startingBalance - endingBalance`)                                                                                                                                  | Proxy balance delta per token after `modifyLiquidities`, with `uint128` clamp                                                                                                                      | Neither facet uses NFPM/PM return values for rate limits. Both measure what left the proxy.                                                                                          |
| **Deposit aggregate accounting**      | Normalized sum of token0 + token1 balance deltas (no clamp)                                                                                                                                                                                | Normalized sum of combined balances before/after, with `_clampedSub` so net receipts (e.g. fees) cannot increase the decrement below zero                                                          | V4 explicitly nets fee receipts against deposit consumption on the aggregate key. V3 aggregate always reflects gross outflows.                                                       |
| **Deposit fee netting (per-asset)**   | Balance delta only counts tokens spent; fee receipts during the same tx are not subtracted from per-asset keys                                                                                                                             | Same: per-asset keys use clamped `starting - ending` per token                                                                                                                                     | Per-asset deposit limits track raw outflow per token. V4 clamp only affects the aggregate normalized total.                                                                          |
| **Withdraw amount measurement**       | Balance delta per token after `decreaseLiquidity` + second `collect` (snapshot taken after an initial `collect`)                                                                                                                           | Balance delta per token after atomic `DECREASE_LIQUIDITY` + `TAKE_PAIR`                                                                                                                            | Both use ending − starting proxy balances, not PM return structs.                                                                                                                    |
| **Withdraw fee inclusion**            | Pre-withdraw `collect()` pulls already-owed fees before the balance snapshot; those fees do not consume withdrawal rate limit. Fees accrued during decrease + post-decrease `collect` are included in the delta                            | Single-step decrease+payout; entire balance increase (principal + fees) is rate-limited                                                                                                            | V3 can realize owed fees without touching withdrawal limits. V4 counts all tokens received in the decrease tx.                                                                       |
| **Withdraw slippage validation**      | Post-execution: `minAmount >= (actualAmount * maxSlippage) / 1e18` per token                                                                                                                                                               | None beyond position manager enforcement of `amount0Min` / `amount1Min`                                                                                                                            | V3 rejects withdrawals where operator mins were loose relative to actual receipts. V4 has no facet-level back-check.                                                                 |
| **Swap rate-limit timing**            | Post-execution: `amountSpent = startingBalance(tokenIn) - endingBalance(tokenIn)`                                                                                                                                                          | Pre-execution: nominal `amountIn`                                                                                                                                                                  | V3 limits what the proxy actually paid. V4 may over-count if the router takes less than `amountIn` (comment: does not account for net tokenIn taken).                                |
| **Swap price protection**             | TWAP (`UniswapV3Utils.consult`) + governance `swapMaxTickDelta` + operator `tickDelta` → `sqrtPriceLimitX96`, plus `minAmountOut > 0` and post-check `amountOut >= minAmountOut`                                                           | Governance `maxSlippage` pre-check on normalized `amountOutMin` vs `amountIn`, plus `amountOut >= amountOutMin` post-check. No TWAP or tick-limit on swaps                                         | V3 enforces an on-chain price band via the router. V4 relies on output minimums and a facet-level “min out not too low” guard only.                                                  |
| **Swap governance params**            | Per pool: `swapMaxTickDelta`, `twapSecondsAgo` (required nonzero for swaps)                                                                                                                                                                | Per poolId: `maxSlippage` only (required nonzero for swaps)                                                                                                                                        | V3 swap safety is oracle- and tick-delta-driven. V4 swap safety is slippage-ratio-driven.                                                                                            |
| **Add-liquidity slippage validation** | TWAP-derived expected amounts; operator `min` must satisfy `min >= expected * maxSlippage / 1e18` (and `maxSlippage` must be set)                                                                                                          | Tick limits only (`tickLowerMin`, `tickUpperMax`, `maxTickSpacing`); operator supplies `amount0Max` / `amount1Max` without TWAP reference                                                          | V3 blocks dangerously loose mins before execution. V4 bounds range geometry, not economic slippage on deposit.                                                                       |
| **Tick-range governance**             | Separate admin setters: `setLiquidityLowerTickBound`, `setLiquidityUpperTickBound`, `setMaxTickDelta`, `setTWAPSecondsAgo`                                                                                                                 | Single atomic `setTickLimits` (or zero triplet to clear). No swap tick-delta concept                                                                                                               | V4 adds `maxTickSpacing` (max tick width). V3 has independent lower/upper liquidity bounds and swap-specific tick delta.                                                             |
| **Tick spacing validation on mint**   | `ticks.lower % tickSpacing == 0` and `ticks.upper % tickSpacing == 0`                                                                                                                                                                      | Delegated to V4 position manager                                                                                                                                                                   | V3 validates alignment client-side; invalid ticks revert in the facet before NFPM call.                                                                                              |
| **Tick re-validation on increase**    | Operator-supplied ticks must match position ticks exactly                                                                                                                                                                                  | Position ticks re-checked against current `TickLimits` on every `increasePosition`                                                                                                                 | V4 can block further deposits if governance tightens limits after mint or if a position was transferred in. V3 only enforces tick match to the position, not live governance bounds. |
| **Ownership check on decrease**       | Required: `ownerOf(tokenId) == proxy`                                                                                                                                                                                                      | Intentionally omitted (comment: worst case is decreasing another account’s position; tokens still go to proxy)                                                                                     | V4 allows decreasing any position in the matched pool. No direct theft, but third-party positions can be modified.                                                                   |
| **TWAP dependency**                   | Required for swaps and add-liquidity validation                                                                                                                                                                                            | Not used                                                                                                                                                                                           | V3 depends on pool oracle accumulators. V4 has no oracle reads in the facet.                                                                                                         |
| **Deadline semantics**                | Operator-supplied `deadline` on NFPM/router calls                                                                                                                                                                                          | Always `block.timestamp` on `modifyLiquidities` and Universal Router `execute`                                                                                                                     | V3 supports future deadlines. V4 operations must complete in the current block.                                                                                                      |
| **Liquidity parameter on deposit**    | `target` token amounts (desired); NFPM computes liquidity                                                                                                                                                                                  | `liquidity` units with `amount0Max` / `amount1Max` caps                                                                                                                                            | Different operator mental model and precision of what gets deposited.                                                                                                                |
| **Return values to caller**           | `addLiquidity` → `(tokenId, liquidity, amounts)`; `removeLiquidity` → `amounts`; `swap` → `amountOut`                                                                                                                                      | All allocator functions return `void`                                                                                                                                                              | V3 propagates outcomes to the Controller caller. V4 observability is events-only from the controller path.                                                                           |
| **Separate fee collection**           | Explicit `collect()` before and after `decreaseLiquidity`                                                                                                                                                                                  | No separate collect; `DECREASE_LIQUIDITY` + `TAKE_PAIR` in one `modifyLiquidities` bundle                                                                                                          | Drives withdraw fee accounting differences (see withdraw fee row).                                                                                                                   |
| **Input validation (facet-level)**    | Swap: `minAmountOut > 0`, `twapSecondsAgo != 0`, `tickDelta <= swapMaxTickDelta`. Deposit: nonzero target, `maxSlippage` set, ticks within governance bounds, post-check `liquidity != 0`. Withdraw: `liquidity` bounds, `maxSlippage` set | Swap: `maxSlippage` set, normalized min-out guard, `poolId`/`PoolKey` match. Liquidity: `tickLimits` set, tick width/order checks, `poolId` match. Mint/increase: proxy ownership on increase only | V3 fails early with facet-specific errors. V4 defers more bounds to external PM/router; fewer economic checks on liquidity ops.                                                      |

## Quick Reference: Admin Setters

| Purpose                   | UniswapV3Facet                                              | UniswapV4Facet                                                                                |
| ------------------------- | ----------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Max slippage (1e18 scale) | `setMaxSlippage(address pool, uint256)`                     | `setMaxSlippage(bytes32 poolId, uint256)`                                                     |
| Liquidity tick bounds     | `setLiquidityLowerTickBound` / `setLiquidityUpperTickBound` | `setTickLimits(poolId, tickLowerMin, tickUpperMax, maxTickSpacing)` — pass all zeros to clear |
| Swap tick guard           | `setMaxTickDelta(pool, uint24)`                             | —                                                                                             |
| TWAP lookback             | `setTWAPSecondsAgo(pool, uint32)`                           | —                                                                                             |
